# 架构与设计（architecture-design）

> 用途：新增模块/服务、改公共接口、跨模块数据流、数据迁移、引入新依赖或新机制前读本文件。给流程、判断标准、错误策略与模板；决定由你来做，但要留下依据。

## 0. 何时读

- 新模块/新服务；改公共 API/CLI/配置/schema/事件；跨模块或跨进程数据流；性能与可靠性架构；数据迁移与回滚；引入新依赖或新机制。
- 小改动（单文件、无接口变化）可跳过流程，但设计决策仍写进 PR/计划。

## 1. 设计流程（7 步）

1. **需求与验收**：目标、非目标、用户可见行为、完成定义；**可测量的质量目标**（性能/可靠性/安全/可维护性）；写明不可接受的失败（数据丢失、越权、停机、静默错误）。
2. **约束**：语言/框架/运行时/部署形态、兼容窗口、性能目标、团队与时间、既有架构与依赖方向（先看现有代码怎么分层）。
3. **探索复用**：先找既有模块/服务/模式（见 SKILL §1 复用清单）；能扩展就不新建。
4. **≥2 个候选方案**：至少一个「最小改动方案」+ 一个「理想方案」；写清各自结构、数据流、改动面与影响模块。
5. **权衡**：用表对比复杂度、风险、成本、可逆性、可测试性、性能、迁移成本、团队熟悉度。
6. **接口先行**：先定公共接口（函数签名/HTTP 路由/事件 schema/配置结构）并评审，再写实现；错误与边界语义在接口层说清。
7. **记录与回填**：写 ADR（见 §6）；实现后回填与计划的偏差及原因。

## 2. 深模块（Deep Module）

概念（Ousterhout《A Philosophy of Software Design》）：模块的「深度」= 接口隐藏的复杂度 ÷ 接口自身的复杂度。好模块 = 简单接口 + 大量隐藏实现。

**判断问题**

- 删掉这个模块后，复杂度会回到调用方吗？不会 → 它是浅模块，合并或删除。
- 调用方要理解多少内部细节才能正确使用？越多越浅。
- 参数/返回值是否暴露实现细节（连接、缓存、重试策略、第三方类型）？是则上移或封装。
- 同一概念是否散落在多个模块（散弹式修改）？是则聚合。

**最小必做**

- 公共接口小、稳定、语义完整；错误与边界在接口层说清。
- 信息隐藏：内部数据结构/第三方类型不泄漏到公共 API。
- 调用方只依赖接口；替换实现不需要改调用方。

**反模式**：为测试暴露内部实现；把配置项当 API 无限膨胀；浅包装层（只做转发）；贫血抽象层。

## 3. 依赖方向

- 依赖单向，指向更稳定/更底层的模块；禁止循环依赖（用 `madge`、`dependency-cruiser` 或构建检查发现）。
- 分层与边界：domain（业务规则）不依赖 infrastructure（DB/HTTP/UI）；用 ports & adapters 隔离外部系统。
- 跨模块通信优先用明确接口或事件；避免共享可变全局状态。
- **DSH 插件场景**：Host 插件提供共享 service；preset 插件只做 scoped 贡献（工具/persona/策略）。提供 service 的插件必须把 provider 与消费者放在同一 isolate realm；不要为一个 preset 场景改 Host 全局。
- 变更影响分析：改接口前列出全部调用点（grep 符号），标记需同步修改的模块与测试。

## 4. 错误策略

| 错误类型 | 例子 | 策略 |
| --- | --- | --- |
| 用户/输入错误 | 参数非法、权限不足 | 明确提示、4xx、不重试 |
| 依赖/瞬时错误 | 网络抖动、限流、超时 | 有界重试 + 退避 + 超时、降级 |
| 业务冲突 | 版本冲突、并发写 | 冲突响应、幂等键、乐观锁 |
| 程序缺陷 | 断言失败、空指针 | fail fast、上报、不吞 |

**最小必做**

- 统一错误表示（错误码/类型/包装），保留 cause；跨层不丢失上下文。
- 重试仅用于幂等操作：有限次 + 退避 + 抖动，且可观测。
- 超时必设且可配置；级联调用要有总时间预算。
- 降级路径明确（缓存/默认值/部分功能），降级要打点且不掩盖错误。

**反模式**：异常当控制流；catch 后无限重试；把错误转成空结果；对外错误码随意变化。

## 5. 迁移与回滚设计

- 兼容性变更用 **expand-contract**：① 扩展（加新字段/双写/新接口，旧路径保留）→ ② 迁移（回填数据、双读校验）→ ③ 切换（读新路径并观察指标）→ ④ 收缩（停写/删旧字段，至少一个发布周期后）。
- 数据迁移：先备份/快照；分批、可中断、可重跑；有校验（行数/校验和/抽样对比）；提供回滚脚本并演练。
- 回滚优先于修复：线上优先回滚（代码回滚 / 关闭 feature flag），再本地修复。
- 发布顺序：先发兼容代码 → 数据迁移 → 启用新路径 → 清理旧逻辑；回滚顺序相反。两者提前写清。
- 不可逆操作（删列/删数据/改协议）单独评审，并需用户明确确认。
- 数据模型与 schema 演进：带版本字段、支持兼容读或明确迁移脚本；新字段先加后切读，最后清理（同 expand-contract 原则）。

## 6. ADR 模板

```markdown
# ADR-000N: <决策标题>

- 状态：proposed / accepted / deprecated / superseded by ADR-000M
- 日期：YYYY-MM-DD
- 背景：问题、约束、现状（为什么现在要决定）
- 决策：选择什么（具体到接口/数据流/边界）
- 备选：考虑过什么、为什么没选（≥1 个）
- 后果：正面/负面、迁移成本、风险与回滚
- 关联：issue / PR / 文档
```

**ADR 自检**

- [ ] 不看聊天记录也能理解背景与决策
- [ ] 至少写了一个备选方案与不选理由
- [ ] 写了后果、风险与回滚方式
- [ ] 编号/日期/状态/关联齐全
- [ ] 决策变化时新增 ADR 或标 superseded，不改历史
- [ ] 若比较过方案，写了 considered options 与 pros/cons（MADR）；可用一句话 Y-statement 摘要：「在 <场景> 下，面对 <问题>，我们选择 <方案> 以获得 <质量>，接受 <代价>」

## 7. 设计自检清单

- [ ] 需求、非目标、不可接受的失败已写清
- [ ] 约束列全（兼容/性能/部署/团队/时间）
- [ ] 复用清单完成，未重复造轮子
- [ ] ≥2 个候选方案 + 权衡表（含最小改动方案）
- [ ] 接口先定并评审，错误/边界语义清楚
- [ ] 依赖方向单向、无循环、跨层隔离
- [ ] 错误策略与超时/重试/降级明确
- [ ] 迁移/回滚可执行并演练（或写明为何不需要）
- [ ] ADR 已记录（小改动写进 PR）

## 8. 横切设计要点

- **安全设计**：入口处威胁建模（信任边界、认证授权模型、密钥生命周期、最小权限）；隐私按最小收集、脱敏、日志不落敏感、明确保留期。
- **可观测性设计**：日志/指标/追踪三件套，traceId 贯穿请求；告警阈值在「设计时」定义，而不是上线后补。
- **性能设计**：容量假设、热点识别、缓存策略与失效、测量方法；无数据不下性能结论。
- **配置与运行环境**：配置集中从环境注入、缺必需项 fail fast、dev/prod 一致、build/release/run 分离（12-Factor）。
- **并发与状态**：共享状态最小化；明确锁/队列/幂等取舍；并发测试点写进测试计划。
- **发布策略**：灰度/回滚顺序、release 不可变、特性开关与 kill switch。

## 9. 技术债与演进

- 记录技术债与其「触发条件」（何时必须还），与功能改动分开提交，预留退出机制。
- 设计评审 gate：方案对比与取舍、风险清单、可回滚性、owner 与确认方式齐全后才进入实现。
